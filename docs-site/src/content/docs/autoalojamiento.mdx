import { Aside, Steps } from '@astrojs/starlight/components'

Open Factura es de código abierto ([AGPL-3.0](https://github.com/xaviigna/openfactura/blob/main/LICENSE)
para el servidor; MIT para el SDK, la CLI y las habilidades). Corre como un solo Worker de
Cloudflare con una base D1: API REST, MCP, webhooks y conciliación.

<Aside type="note" title="Sin panel">
  Lo autoalojado no trae panel web: se administra con la API, la CLI o tu agente. El panel, el alta
  guiada y la certificación automática son parte de [Open Factura Cloud](https://openfactura.co/api).
</Aside>

## En tu equipo

Requisitos: [Bun](https://bun.sh) (el repositorio fija `bun@1.4.4` en `packageManager`) y Node 20+.

<Steps>

1. **Clona, instala y arranca el servidor.**

   ```bash
   git clone https://github.com/xaviigna/openfactura && cd openfactura
   bun install
   cp server/.dev.vars.example server/.dev.vars     # completa los secretos (openssl rand -base64 32/48)
   echo "MH_SIMULADO=1" >> server/.dev.vars         # simulador del MH: emite sin credenciales de Hacienda
   echo "WEBHOOKS_LOCAL=1" >> server/.dev.vars      # webhooks a http://localhost (sólo desarrollo)
   bun run build
   cd server && bun run db:migrate:local
   bun run dev                                      # API y MCP en :8788; déjalo corriendo
   ```

   Esta terminal queda ocupada: el resto va en otra, desde la raíz del repositorio.

   <Aside type="note">
   Arranca el servidor con `bun run dev` dentro de `server/`. En la raíz, `bun run dev` también
   levanta la documentación y el `dev` de la CLI, que termina con «Falta el comando» y detiene todo.
   </Aside>

2. **Archivos de ejemplo.** Datos inventados, pero con códigos de catálogo válidos (departamento
   `06`, municipio `23`, distrito `14` y actividad `62010`, que pertenecen a San Salvador):

   ```bash
   mkdir -p ~/openfactura-ejemplo
   cat > ~/openfactura-ejemplo/emisor.json <<'EOF'
   {
     "nit": "0614-010190-101-0",
     "nrc": "1234567",
     "nombre": "EMPRESA DE PRUEBA, S.A. DE C.V.",
     "nombreComercial": "Empresa de Prueba",
     "codActividad": "62010",
     "descActividad": "Programación informática",
     "departamento": "06",
     "municipio": "23",
     "distrito": "14",
     "complemento": "Calle de Prueba #123, San Salvador",
     "telefono": "22220000",
     "correo": "facturas@empresa-de-prueba.example"
   }
   EOF
   cat > ~/openfactura-ejemplo/factura.json <<'EOF'
   {
     "tipoDte": "01",
     "datos": {
       "items": [
         { "descripcion": "Servicio de consultoría", "cantidad": 3, "precioUni": 56.5, "tipoItem": 2 }
       ]
     }
   }
   EOF
   cat > ~/openfactura-ejemplo/ccf.json <<'EOF'
   {
     "tipoDte": "03",
     "datos": {
       "receptor": {
         "nit": "0614-290786-103-1",
         "nrc": "234567-8",
         "nombre": "CLIENTE DE PRUEBA, S.A. DE C.V.",
         "codActividad": "46900",
         "descActividad": "Venta al por mayor de otros productos",
         "direccion": {
           "departamento": "06",
           "municipio": "23",
           "distrito": "14",
           "complemento": "Av. Olímpica #100"
         },
         "correo": "compras@cliente-de-prueba.example"
       },
       "items": [{ "descripcion": "Licencia anual", "cantidad": 1, "precioUni": 100, "tipoItem": 2 }]
     }
   }
   EOF
   ```

   En la factura (`01`) `precioUni` incluye IVA; en el CCF (`03`) va sin IVA
   ([Emitir documentos](/guias/emitir/)). El NIT y el NRC son de mentira; el
   NIT debe tener 14 dígitos (o 9) y el NRC de 2 a 8.

3. **Crea la organización y conecta el simulador.** Desde la raíz del repositorio, en otra terminal.
   Necesitas `jq`. La CLI recién compilada se ejecuta con `node packages/cli/dist/index.js` (es el
   `bin` `openfactura` de `packages/cli/package.json`); la función de abajo la deja como
   `openfactura`. `--profile local` evita pisar la sesión que tengas en `~/.config/openfactura`.

   ```bash
   REPO=$PWD
   openfactura() { node "$REPO/packages/cli/dist/index.js" "$@"; }
   export OPENFACTURA_PROFILE=local OPENFACTURA_URL=http://localhost:8788
   export OPENFACTURA_ADMIN_TOKEN=$(grep '^ADMIN_TOKEN=' server/.dev.vars | cut -d= -f2-)

   export ORG=$(openfactura alta "Empresa de Prueba" --json | jq -r .organizacion.id)
   admin() { curl -sS "$OPENFACTURA_URL/api/v1$1" -H "Authorization: Bearer $OPENFACTURA_ADMIN_TOKEN" \
     -H "X-Organizacion: $ORG" -H 'Content-Type: application/json' "${@:2}"; }

   admin /emisor -X PUT -d @$HOME/openfactura-ejemplo/emisor.json   # datos del emisor
   admin /emisor/credenciales-prueba -X POST                         # certificado y clave simulados
   ```

   `alta` crea la organización y deja una clave `of_test_…` en el perfil `local`; con
   `OPENFACTURA_PROFILE=local` los comandos siguientes la usan. Si prefieres no compilar la CLI,
   `npx @openfactura/cli` (la versión publicada en npm) hace lo mismo: sustituye la función
   `openfactura` por ese comando.

4. **Emite y consulta.**

   ```bash
   openfactura dte emitir ~/openfactura-ejemplo/factura.json --json | tee /tmp/dte.json | jq '{estado, total}'
   openfactura dte get "$(jq -r .codigoGeneracion /tmp/dte.json)"
   openfactura dte emitir ~/openfactura-ejemplo/ccf.json --json | jq '{estado, total}'
   ```

   El estado debe ser `procesado`, con `selloRecibido`; la factura suma `169.5`. Con
   `dte pdf <codigo> -o factura.pdf` obtienes la representación gráfica.

</Steps>

### Establecimientos y puntos de venta

Al guardar el emisor por primera vez se crean solos la casa matriz **`M001`** (tipo `02`) y su punto
de venta **`P001`**. Con eso ya emites: el número de control sale como `DTE-01-M001P001-…`. No
tienes que crear nada más para el recorrido de arriba.

Crea los tuyos sólo si Hacienda te asignó otros. Los códigos (`M001`, `S002`, `P002`…) los asigna el
MH: usa los de tu inscripción.
`codMh` de un establecimiento es `M`, `B`, `S` o `P` y tres dígitos; el de un punto de venta, `P` y tres
dígitos. Ambos exigen `emisor:write` (el operador con `ADMIN_TOKEN`; las claves de API no) y devuelven
`201` con la lista de establecimientos y sus puntos de venta:

```bash
# tipo: 01 sucursal/agencia, 02 casa matriz, 04 bodega, 07 patio (por defecto 01)
admin /establecimientos -X POST -d '{"nombre":"Sucursal Centro","tipo":"01","codMh":"S001"}' \
  | jq -r '.[] | "\(.id) \(.codMh)"'

admin /puntos-venta -X POST -d '{"establecimientoId":"<id del establecimiento>","nombre":"Caja 2","codMh":"P002"}'
```

Un código repetido responde `codigo_repetido`. Para emitir desde otro punto de venta, pasa su
`puntoVentaId` en el cuerpo de `POST /dte` (si no, se usa el primero del emisor). Los datos de dirección y teléfono que
no indiques en el establecimiento se toman del emisor.

## En tu cuenta de Cloudflare

<Aside type="caution">
El plan gratuito de Workers limita la CPU a 10 ms por petición. Firmar (RSA) y generar el PDF superan
ese límite: usa el plan de pago de Workers.
</Aside>

<Steps>

1. **Base de datos.**

   ```bash
   cd server
   bunx wrangler d1 create openfactura
   ```

   Copia el `database_id` a `server/wrangler.jsonc` y aplica las migraciones con
   `bun run db:migrate:remote`.

2. **Configuración.** En `server/wrangler.jsonc` cambia `vars.APP_URL` por tu URL pública. Luego
   los secretos:

   ```bash
   openssl rand -base64 32 | bunx wrangler secret put BETTER_AUTH_SECRET
   openssl rand -base64 32 | bunx wrangler secret put CRED_KEK_V1
   openssl rand -base64 48 | tee admin-token.txt | bunx wrangler secret put ADMIN_TOKEN
   ```

   `ADMIN_TOKEN` es tu credencial de operador: crea organizaciones y administra el emisor, sus
   credenciales del MH y las claves de API. Guárdalo como una contraseña.

   `CRED_KEK_V1` cifra las credenciales del MH de todos los emisores. **Guarda una copia fuera de
   Cloudflare.** No definas `WEBHOOKS_LOCAL` en producción.

3. **Desplegar.**

   ```bash
   cd .. && bun run deploy
   ```

4. **Primer uso.** `npx @openfactura/cli alta "Mi Empresa" --url https://TU-DOMINIO`, y con
   `ADMIN_TOKEN` + `X-Organizacion`: `PUT /api/v1/emisor`, `PUT /api/v1/emisor/credenciales/00`
   (contraseña de API, certificado `.crt` y su contraseña) y `POST /api/v1/emisor/probar`. Paso a paso
   en [`docs/self-hosting.md`](https://github.com/xaviigna/openfactura/blob/main/docs/self-hosting.md).

</Steps>

## Variables

| Nombre                    | Tipo    | Descripción                                                          |
| ------------------------- | ------- | -------------------------------------------------------------------- |
| `APP_URL`                 | var     | URL pública del servicio                                             |
| `BETTER_AUTH_SECRET`      | secreto | Firma de sesiones                                                    |
| `ADMIN_TOKEN`             | secreto | Credencial del operador (32+ caracteres); sin ella no hay administración |
| `CRED_KEK_V1` (`V2`, …)   | secreto | Llave maestra AES-256, 32 bytes en base64                            |
| `LIMITE_CLAVE_POR_MINUTO` | var     | Peticiones por minuto por clave de API (120)                         |
| `TRUSTED_ORIGINS`         | var     | Orígenes adicionales de confianza, separados por coma                |
| `MH_BASE_URL`             | var     | Sustituye la URL del MH (sólo para pruebas)                          |
| `MH_SIMULADO`             | var     | `1` permite `POST /emisor/credenciales-prueba` (simulador del MH, ambiente `00`) |
| `WEBHOOKS_LOCAL`          | var     | `1` permite webhooks a `http://localhost` (sólo desarrollo)          |
| `TURNSTILE_SECRET`        | secreto | Cloudflare Turnstile (opcional). Con él, el registro, el inicio de sesión y la petición del enlace de recuperación exigen el token del widget |
| `TURNSTILE_SITE_KEY`      | var o secreto | Clave pública del widget; el panel la recibe en `GET /api/v1/acceso` |
| `TURNSTILE_HOSTNAMES`     | var o secreto | Dominios donde se muestra el widget, separados por coma; con el secreto y sin dominios se rechaza todo |

### Cloudflare Turnstile (opcional)

Con `TURNSTILE_SECRET` definido, `POST /api/auth/sign-up/email`, `/api/auth/sign-in/email` y
`/api/auth/request-password-reset` exigen el token del widget en el encabezado `x-turnstile-token`. El
servidor lo comprueba con Cloudflare (`siteverify`, con la IP de `cf-connecting-ip`) **antes** de
calcular el hash de la contraseña, y exige que la acción sea la de esa pantalla (`signup`, `login` o
`password_reset`) y que el dominio esté en `TURNSTILE_HOSTNAMES`. Sin token, con uno inválido, o si
Cloudflare no responde: `403 turnstile_invalido`. Las tres variables pueden ser secretos o vars; sin
`TURNSTILE_SECRET` todo funciona como antes. No pongas `localhost` en los dominios de producción.

Para probar en local o en CI, usa las claves de prueba de Cloudflare: la del sitio
`1x00000000000000000000AA` con el secreto `1x0000000000000000000000000000000AA` siempre pasan; los
secretos `2x0000000000000000000000000000000AA` (y la clave del sitio `2x00000000000000000000AB`)
siempre bloquean. Con ellas, Cloudflare responde sin `action`, con `hostname` `example.com` y la marca
`metadata.result_with_testing_key`: sólo entonces el servidor acepta la respuesta sin acción, y
`example.com` tiene que estar en `TURNSTILE_HOSTNAMES` (p. ej. `localhost,example.com`). Si el
widget no carga (un bloqueador o un firewall), el panel lo dice y ofrece reintentar.

## Rotar la llave maestra

1. `bunx wrangler secret put CRED_KEK_V2` con una llave nueva. Lo nuevo se cifra con V2; lo anterior
   se sigue descifrando con V1.
2. Vuelve a guardar las credenciales de cada emisor.
3. Cuando ningún valor empiece por `v1.`, elimina `CRED_KEK_V1`.

El documento OpenAPI de tu instalación queda en `https://TU-DOMINIO/api/v1/openapi.json`.
